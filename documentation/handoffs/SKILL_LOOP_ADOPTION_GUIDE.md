# Skill loop — cross-repo adoption guide

> **Reference implementation (plate-harness):** the home repository replaced 37 loosely connected v0.42.0 skills with one product-owner loop of 21 skills in four layers, so an agent always knows which stage it is in and the owner is asked only at two stops. This guide explains **what** to add in **your** repository and **how** to port it, including the full rename map. Paths in §3 are **illustrative** — adapt everything to your layout.  
> **SSOT (home repo):** [`router/references/loop-map.md`](../../.agents/skills/router/references/loop-map.md) (stages and stops), [`router/references/catalog.md`](../../.agents/skills/router/references/catalog.md) (registry), [`meta-write-skill/references/skill-template.md`](../../.agents/skills/meta-write-skill/references/skill-template.md) (structure)  
> **Layer model:** [`DOC_AGENT_WORKFLOW_LAYERS.md`](../DOC_AGENT_WORKFLOW_LAYERS.md)

## What it is / what it is not

| It is | It is not |
|---|---|
| One loop (`router` → backlog → refine → plan → build → check → ship → verdict) with two owner stops | A set of independent slash commands the owner picks from |
| Four layers by name prefix: `router`, `loop-*`, `spec-*` (≥ 2 loop callers), `meta-*` (harness upkeep) | Aliases for the old names — old folders are deleted, not redirected |
| An admission check (catalog row + template + reciprocal edges) run on commit and in CI | A style guide that relies on reviewers |
| Rules that hold always-on corrections; skills that hold procedures | Rules that restate skill procedures |

## 1. Problem this addresses

Without one loop, agents guess which skill applies, skills restate each other, the owner is asked about choices the agent could make, and decisions get lost between sessions. Renames and merges also break links silently.

## 2. What to introduce in a repository

### 2.1 Artifacts to create (generic names)

- A **router** skill and a **loop map** reference (stages, stops, where a lap stands).
- Seven **loop** skills, one per stage, each with evals.
- **Specialist** skills only for helpers that at least two stages call; single-caller helpers stay references inside their caller.
- **Meta** skills for writing skills, auditing and intaking harness content, lessons, rule grading.
- A **skill template**, a **catalog** (registry) and an **admission check** script, plus a generated mirror for tools that read skills from another folder.

### 2.3 Boundaries

- Keep fork-specific skills; give each a catalog row and a layer prefix, or list it as external.
- Keep fork-specific rules; only the procedure parts that moved into skills should leave them.

## 4. Portable substance

- **Two stops:** the owner confirms what is built (end of refine) and judges the preview (verdict: Pass / Change / Drop). Between them the agent works alone and asks only on a short stop list (conflict with a recorded decision, true tie, new dependency, patch on top vs structural fix, data or irreversible change, cost).
- **The agent sizes the work** (XS / S / M) and cuts larger work into laps; one lap is one branch.
- **Decisions live with what they govern** (feature READMEs, the vision, rules), not in session notes.
- **Edges are links:** every skill lists In, Out, Calls, Called by, Next and Owner stops, and Calls ⇄ Called by must agree.
- **Guards fire from rules:** always-on rules trigger the specialists (layer check, reuse check, naming); the specialist holds the procedure.

## 5. Teaching example (one instance — home repository)

> **Illustrative only.** Reuse the pattern, not the names.

A merge of two debugging skills into `spec-debug-runtime` kept both bodies word for word as references (`scientific-method.md`, `hypothesis-mode.md`), wrote a short template `SKILL.md` around them, removed the router tiebreak between the two old skills, and kept the always-on parts (logging, simplify first) in the debugging rule.

## 6. Workflow (human and agent)

The owner says what they want or "next"; the router finds the stage; the loop runs to the preview; the owner answers Pass, Change or Drop. Harness upkeep runs through the `meta-*` skills, called directly.

## 7. How to adopt in another repository

### 7.1 Step-by-step

1. Drop this guide in your harness inbox and run your intake skill (here: `meta-intake-harness`).
2. Apply the rename map in §2.2: rename or merge folders, then search the whole repo for each old name and update links.
3. Add the template, catalog, admission check and mirror; register every skill.
4. Move procedures out of rules into the skills that own them; keep corrections in the rules.
5. Run the admission check, the link check and an audit (here: `meta-audit-harness`).

### 7.2 Minimum vs recommended

| Minimum | Recommended |
|---|---|
| Router + loop map + the seven loop skills | Plus port maps, evals for loop skills, and the admission check in CI |

### 7.3 Target repo discovery checklist

- [ ] Which old skills exist in your repo, and which are fork-only?
- [ ] Where do your skills live, and which tools read them from another folder?
- [ ] Which rules hold procedures that a skill should own?
- [ ] What is your branch model and where is the preview?

### 7.4 Illustrative mapping (home repo → your repo)

| Home repo | Your repo |
|---|---|
| `.agents/skills/` | your skills folder |
| `src/config/app-tasks.json` (backlog) | your backlog |
| Preview per PR | your preview or staging surface |

### 7.5 Adoption anti-patterns

- Keeping old names as alias skills — they double the trigger surface and drift.
- Copying rule bodies into skills (or back) — one home per instruction.
- A specialist with one caller — make it a reference.

## 8. Edge cases (optional)

A fork that customized an old skill: port the customization into the new skill's reference that holds the old body, and record it in the port map as kept.

## 9. Summary

One loop, four layers, two owner stops, links that a script checks. Rename with the map in §2.2, delete the old folders, and let the admission check and the audit catch what was missed.
